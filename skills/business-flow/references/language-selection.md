# Project-driven report language

The calling model decides the report language from the target repository's substantive documentation **and source-code comments**. This is semantic analysis, not a character-count detector. The renderer consumes a recorded decision; it does not silently guess language or translate generated business descriptions.

1. Inspect the main README and relevant architecture/domain docs, then sample comments/docstrings from the actual modules in analysis scope. Prefer explanatory business comments over short TODOs. Ignore code tokens, identifiers, string literals, language keywords, vendored/generated files, copied license headers, build outputs and earlier generated reports when judging language. Repository instructions govern behavior but skill text and chat language are not project-language evidence.
2. Compare the two sources. When they agree, use that language. If one source has little substantive text, use the stronger source and record the missing evidence. For multilingual README variants, use the project's declared primary documentation language; focus-module docs/comments may be more representative for a narrowly scoped report.
3. When substantive docs and business comments conflict without a clear primary language, ask one concise language question before generating final prose. Explain the conflict with actual files. Do not default to Chinese because the conversation is Chinese, or English because function names are English. If neither source supplies useful evidence and no user override is given, use English and record `selection: fallback` and that limitation.
4. An explicit user request for an output language overrides this automatic decision. The language of the user's requirement alone is not an explicit override. Record `selection: override` and the request; otherwise use `project` with file/line evidence and a short rationale in the selected language.

Use the selected language for graph title, node/edge labels, summaries, inputs/outputs, state explanations, rule consequences, impact reasons, regression suggestions, limitations, language rationale, and **all HTML controls, legends, tooltips, accessibility labels and status messages**. Keep identifiers, IDs, paths, formulas, exact predicates and explicitly quoted source/error text unchanged. Translate `impact.request` for presentation if needed, retaining the original text in optional `impact.originalRequest` metadata for provenance.

Add `language: {code, selection, reason, evidence}` to every new graph, using a BCP-47-style language code, e.g. `en` or `zh-CN`. Cite both docs and comments when available. Never fabricate comment evidence when the repository has no comments. References must be current repository-relative paths with one-based line ranges; these participate in snapshot hashing. The overview sidebar shows the rationale.

HTML resources are localized through [../assets/locales.json](../assets/locales.json). The renderer includes built-in English and Simplified Chinese catalogs. English regional tags reuse English; `zh`, `zh-CN`, `zh-Hans`, `zh-Hans-CN` reuse Simplified Chinese. Other languages (including Traditional Chinese) require a complete `ui` object translated by the calling model, with the same keys and interpolation placeholders as the English catalog. Use it as a key/template reference, not as instructions to change the selected project language. Partial custom catalogs fail validation to prevent mixed-language fallback. Generate one consistent language per report; this is not an in-browser translation switch.

When regenerating a report in a different language, translate its business prose and replace/remove the old `ui` catalog together. Changing only `language.code` does not translate graph content. Old reports without `language` retain their historical Chinese UI for compatibility; never omit the field on newly analyzed reports. Verify rendered static controls and dynamic node/impact panels in the selected language; distinguish actual model-language selection quality from catalog/renderer tests.
